# SECTION 17 — Missing Documentation

รายการนี้ระบุส่วนของโค้ดที่ควรมีเอกสารเพิ่ม พร้อมเหตุผลว่าทำไมจึงจำเป็น

## 17.1 ระดับวิกฤต — ไม่มีเอกสารแล้วทำงานต่อไม่ได้

### 17.1.1 Schema จริงของฐานข้อมูลแจ้งเตือน
- ปัญหา — โค้ดใช้คอลัมน์ `push_subscription` ที่ไม่มีใน migration ใด และ `fcm_token` ยังเป็น NOT NULL
- ต้องมี — migration ที่สะท้อน schema จริงบน production หรืออย่างน้อยเอกสารบอกว่า schema จริงต่างจาก migration อย่างไร
- ผลถ้าไม่มี — สร้างสภาพแวดล้อมใหม่ไม่ได้ และ deploy migration ทั้งชุดจะทำให้ระบบแจ้งเตือนพัง

### 17.1.2 ลำดับการโหลดสคริปต์และเหตุผลของแต่ละลำดับ
- ปัญหา — `index.html` โหลด 20 ไฟล์ตามลำดับที่ห้ามสลับ แต่ไม่มีคอมเมนต์อธิบายว่าทำไมต้องเรียงแบบนี้
- ต้องมี — คอมเมนต์ในบรรทัดของแต่ละ `<script>` บอก dependency เช่น
  `<!-- ต้องมาหลัง app_v2.js เพราะ patch App._ledgerFlows -->`
- ผลถ้าไม่มี — คนที่เพิ่มสคริปต์ใหม่มีโอกาสสูงมากที่จะวางผิดตำแหน่งแล้วแอปพังแบบเงียบ ๆ

### 17.1.3 ฟังก์ชัน render ที่ถูกนิยามซ้ำ
- ปัญหา — `renderDashboard` มี 5 นิยาม `renderReports` 5 นิยาม แต่ไม่มีที่ใดบอกว่าตัวไหนใช้จริง
- ต้องมี — คอมเมนต์เหนือแต่ละนิยามว่า "ตัวนี้ถูกทับโดยบรรทัด XXXX" หรือ "ตัวนี้เป็นตัวสุดท้าย"
- ผลถ้าไม่มี — นักพัฒนาแก้บั๊กในนิยามที่ตายแล้วโดยไม่รู้ตัว

### 17.1.4 สัญญาของ `App._ledgerFlows` และวิธี patch ที่ถูกต้อง
- ปัญหา — `CLAUDE.md` เตือนว่า `loans_v2.js` ต้อง wrap แต่ `bnpl.js` ต้องแก้ในตัว โดยไม่อธิบายเหตุผล
- ต้องมี — คอมเมนต์บล็อกเหนือ `_ledgerFlows` อธิบายกติกา
  (โมดูลที่มี store แยกจาก `S.transactions` ต้อง wrap; โมดูลที่ใช้ `S.transactions` ต้องเพิ่ม case ในตัว)
- ผลถ้าไม่มี — การเพิ่มโมดูลใหม่จะทำให้ยอดกระเป๋าถูกนับซ้ำหรือขาดหาย

## 17.2 ระดับสูง — โค้ดซับซ้อนที่ต้องอธิบาย

### 17.2.1 Benefit Rule Engine
- ขอบเขต — `App.applyBenefitRule`, `calculateSelectedRewardEstimate`, `getOptimalBenefitSelection`,
  `getSuggestedBenefitRules`, `getRuleCycleUsage`, `getBenefitCapBreakdown`, `normalizeBenefitRule`
- ต้องมี — เอกสารแยกที่อธิบาย
  - โครงสร้างของ rule object ทุกฟิลด์ (ตอนนี้ต้องอ่านโค้ดเพื่อรู้ว่ามีฟิลด์อะไรบ้าง)
  - ลำดับการคำนวณเมื่อมีหลายกฎเข้าเงื่อนไขพร้อมกัน
  - นิยามของเพดาน (ต่อรายการ / ต่อรอบ / ต่อร้าน / ต่อช่องทาง) และการนับ
  - ความหมายของฟิลด์ทั้ง 50 ที่ `applyBenefitRule` คืน และเหตุผลที่ `_slimRewardEstimate` เก็บไว้แค่ 12
- เหตุผล — เป็นตรรกะที่ซับซ้อนที่สุดในระบบและกระทบตัวเงินโดยตรง

### 17.2.2 Finance Intelligence
- ขอบเขต — 50 ฟังก์ชันที่ export จาก `finance_intelligence.js`
- ต้องมี
  - สูตรของ `healthScore` และน้ำหนักแต่ละองค์ประกอบ
  - โมเดลที่ `forecasts` ใช้ (moving average? linear regression? — ต้องอ่านโค้ดถึงจะรู้)
  - นิยามของ archetype แต่ละแบบใน `inferredArchetype`
  - โครงสร้างของ feature store และเงื่อนไข freshness
  - ความหมายของ MAPE และ bias ใน `forecastAccuracySummary`
- เหตุผล — ผู้ใช้เห็นตัวเลขพยากรณ์แต่ไม่มีใครอธิบายที่มาได้

### 17.2.3 AI Insights — เกณฑ์ของแต่ละกฎ
- ขอบเขต — INS-01 ถึง INS-16
- ต้องมี — ตารางที่ระบุต่อกฎ: เงื่อนไขที่ทำให้ยิง, severity/urgency/impact ที่ให้, action ที่แนบ, และ TTL
- เหตุผล — ปัจจุบันต้องอ่าน `runRules` ทั้ง 350 บรรทัดเพื่อตอบคำถามว่า "ทำไมถึงเตือน"

### 17.2.4 การคำนวณรอบบิลบัตรเครดิต
- ขอบเขต — `credit_card_cycles.js`
- ต้องมี — เอกสารพร้อมตัวอย่างเชิงตัวเลข เช่น
  "บัตรตัดรอบวันที่ 25 ครบกำหนดวันที่ 23 ของเดือนถัดไป ถ้าวันที่ 23 ตรงเสาร์จะเลื่อนเป็น 22"
- เหตุผล — โมดูลนี้เขียนดีและมีเทสต์ แต่กติกาทางธุรกิจ (โดยเฉพาะการเลื่อนย้อนหลังเมื่อชนวันหยุด) ไม่ชัดเจนจากชื่อฟังก์ชัน
- หมายเหตุ — มีเอกสารที่เกี่ยวข้องอยู่แล้วที่ `docs/superpowers/plans/2026-06-03-credit-card-billing-ux.md` (864 บรรทัด)
  แต่เป็นเอกสารแผนงาน ไม่ใช่คู่มืออ้างอิง

### 17.2.5 Quick Capture Parser
- ขอบเขต — `parseQuickCapture` และฟังก์ชันช่วย 15 ตัว
- ต้องมี — ตารางตัวอย่าง input → output ที่ครอบคลุมทุกกลยุทธ์
  โดยเฉพาะ Tier 4 phonetic matching ที่ตรรกะซับซ้อนมาก (romanize → consonant skeleton → Levenshtein → subsequence check)
- เหตุผล — ยังไม่มีเทสต์สำหรับ parser นี้เลย (ไม่พบ `quick_capture` ใน `tests/`) และเป็นฟีเจอร์ที่ผู้ใช้พึ่งพามาก

### 17.2.6 ระบบ History / Back-button
- สถานะ — มีคอมเมนต์อธิบายที่ดีมากอยู่แล้ว (บรรทัด 24563–24597 ยาว 35 บรรทัด)
- ที่ขาด — รายการ dialog ที่ไม่ครอบคลุม (คอมเมนต์บอกว่า "a handful of one-off dialogs ... are not covered here"
  แต่ไม่ระบุว่าคือตัวไหนบ้าง)
- ต้องมี — รายชื่อ dialog ที่ยังไม่รองรับปุ่มย้อนกลับ เพื่อให้แก้ได้ทีละตัว

## 17.3 ระดับกลาง — โครงสร้างข้อมูล

### 17.3.1 Schema ของ Transaction
- ปัญหา — object ธุรกรรมมีมากกว่า 45 ฟิลด์ ที่กระจายอยู่หลายที่ในโค้ด ไม่มีเอกสารรวม
- ต้องมี — เอกสารอ้างอิงพร้อมระบุว่าแต่ละฟิลด์
  ใช้กับ tx ชนิดไหน / ใครเขียน / ใครอ่าน / บังคับหรือไม่ / มีค่าเริ่มต้นอะไร
- (เอกสารชุดนี้ SECTION 8.2 ได้เริ่มไว้แล้ว แต่ควรอยู่ใกล้โค้ด)

### 17.3.2 Schema ของ Wallet และความแตกต่างตามประเภท
- ปัญหา — ฟิลด์ที่ใช้ต่างกันมากระหว่างประเภท (บัตรเครดิตมี 12 ฟิลด์เฉพาะ, BNPL มี 3, กระเป๋าลงทุนมี 4)
- ต้องมี — ตารางฟิลด์ × ประเภท

### 17.3.3 คีย์ localStorage ทั้งหมด
- ปัญหา — มี 37 คีย์ใน `KEYS` และอีกกว่า 20 คีย์นอกระบบ กระจายในหลายไฟล์
- ต้องมี — รายการรวมพร้อมระบุ เจ้าของ / รูปแบบ / อยู่ใน backup หรือไม่ / ถูกลบตอน reset หรือไม่
- (เอกสารชุดนี้ SECTION 8.1 ได้รวบรวมไว้แล้ว)

  import/export, ล็อก/ปลดล็อก, ล็อกอินและซิงก์, แจ้งเตือน, โหมดมืด, ปุ่มย้อนกลับทุกชั้น

## 19.2 ใครพึ่ง `App` และ `S` (global)

พึ่งแบบบังคับ (พังทันทีถ้าไม่มี)

- `bnpl.js` — ทุกจุดที่แตะ `App` และ `S` มี optional chaining
- `onboarding.js` — `if (typeof App === 'undefined' || typeof S === 'undefined') return`
- `calculations.js` — try/catch ครอบทุกจุดที่เรียก `App`

ไม่พึ่งเลย (pure)
- `credit_card_cycles.js`, `crypto_vault.js`, `gold_market.js`, `ask_my_money_core.js`, `thai_bank_holidays.js`

# SECTION 20 — Complete Functional Specification

เอกสารส่วนนี้เขียนในรูปแบบที่ Developer, QA, UX/UI Designer, Product Owner และ Business Analyst ใช้อ้างอิงได้ทันที
ทุกข้อความอ้างอิงพฤติกรรมจริงของโค้ด

## FS-1 ขอบเขตของระบบ

### FS-1.1 สิ่งที่ระบบทำ
1. บันทึกและจัดเก็บธุรกรรมการเงินส่วนบุคคล 8 ชนิด
2. คำนวณยอดคงเหลือของกระเป๋าเงิน 9 ประเภทแบบ deterministic จาก ledger
3. บริหารบัตรเครดิต: รอบบิล วันครบกำหนด วงเงิน วงเงินร่วม สิทธิประโยชน์ และการชำระ
4. บริหารการผ่อนชำระทั้งแบบบัตรเครดิตและแบบ BNPL
5. บริหารการเงินร่วมกับผู้อื่น: หารบิล ค่าใช้จ่ายร่วม และเงินให้ยืม
6. วางแผนการเงิน: งบประมาณ รายการรอจ่าย รายการประจำ เป้าหมาย และแผนชีวิต
7. วิเคราะห์: รายงาน 8 มุมมอง คำแนะนำเชิงกฎ 16 ประเภท พยากรณ์ และจำลองสถานการณ์
8. เก็บรักษาข้อมูล: สำรอง กู้คืน และซิงก์ข้ามอุปกรณ์แบบเข้ารหัสฝั่งผู้ใช้
9. ป้องกันข้อมูล: ล็อกแอปด้วย PIN และ biometric
10. เตือนความจำ: แจ้งเตือน Web Push ตามกฎ 13 ทริกเกอร์

### FS-1.2 สิ่งที่ระบบไม่ทำ (ยืนยันว่าไม่พบในโค้ด)
1. ไม่เชื่อมต่อธนาคารโดยตรง ไม่ดึงรายการเดินบัญชีอัตโนมัติ
2. ไม่รองรับผู้ใช้หลายคนในบัญชีเดียวหรือการแชร์ข้อมูลระหว่างผู้ใช้
3. ไม่มีระบบสิทธิ์ ไม่มี role ไม่มี admin panel
4. ไม่รองรับหลายสกุลเงินในระดับธุรกรรม (สกุลเงินอยู่ที่ระดับกระเป๋า FCD เท่านั้น)
5. ไม่แนบไฟล์หรือรูปสลิปกับธุรกรรม
6. ไม่มีการ OCR สลิปหรืออ่าน SMS ธนาคาร
7. ไม่มีการส่งออกเป็น PDF
8. ไม่มี API สาธารณะให้ระบบอื่นเรียก
9. ไม่มี realtime collaboration
10. ไม่มีการคำนวณภาษี

## FS-2 ข้อกำหนดเชิงหน้าที่ (Functional Requirements)

### FR-01 การบันทึกธุรกรรม
- FR-01.1 ระบบต้องรับธุรกรรม 3 ชนิดผ่าน UI หลัก: รายจ่าย รายรับ และโอนระหว่างกระเป๋า
- FR-01.2 ระบบต้องรับจำนวนเงินผ่านแป้นตัวเลขในแอป จำกัดจำนวนเต็มไม่เกิน 10 หลัก และทศนิยมไม่เกิน 2 ตำแหน่ง
- FR-01.3 ระบบต้องรองรับการคำนวณในช่องจำนวนเงิน (บวก ลบ คูณ หาร)
- FR-01.4 ระบบต้องปฏิเสธการบันทึกที่จำนวนเงินไม่มากกว่า 0
- FR-01.5 ระบบต้องปฏิเสธรายจ่ายที่ทำให้กระเป๋าที่ไม่ใช่บัตรเครดิตหรือ BNPL ติดลบ
- FR-01.6 ระบบต้องปฏิเสธรายจ่ายที่เกินวงเงินคงเหลือของบัตรเครดิต โดยคำนวณวงเงินร่วมและยอดผ่อนที่ยังไม่ถึงกำหนดด้วย
- FR-01.7 ระบบต้องปฏิเสธการโอนระหว่างกระเป๋าที่ไม่ใช่ประเภท bank/cash/ewallet/saving
- FR-01.8 ระบบต้องบังคับให้รายจ่ายและรายรับมีหมวดหมู่
- FR-01.9 ระบบต้องจำกัดความยาว: ชื่อร้าน 100 ตัวอักษร หมายเหตุ 1000 ตัวอักษร
- FR-01.10 ระบบต้องปรับชื่อร้านให้ตรงกับรายการร้านค้าที่มีอยู่โดยไม่สนตัวพิมพ์ใหญ่เล็ก
- FR-01.11 เมื่อผู้ใช้แก้ไขธุรกรรม ระบบต้องคำนวณยอดคงเหลือโดยถอนผลของธุรกรรมเดิมออกก่อนตรวจสอบ
- FR-01.12 หลังบันทึกสำเร็จ ระบบต้องคำนวณยอดกระเป๋าใหม่ทั้งหมด บันทึกลง storage และแสดงข้อความยืนยัน

### FR-02 การผ่อนชำระ
- FR-02.1 เมื่อผู้ใช้เลือกผ่อนตั้งแต่ 2 งวดขึ้นไป ระบบต้องสร้างธุรกรรมแยกหนึ่งรายการต่องวด
- FR-02.2 ทุกงวดต้องมี `installmentGroupId` เดียวกัน และมีเลขงวดกำกับ
- FR-02.3 ยอดต่องวดต้องปัดลง 2 ตำแหน่ง และงวดสุดท้ายต้องรับเศษ เพื่อให้ผลรวมเท่ากับยอดเต็ม
- FR-02.4 งวดที่วันครบกำหนดยังไม่มาถึงต้องไม่กระทบยอดคงเหลือของกระเป๋าและยอดหนี้บัตร
- FR-02.5 เมื่อวันของงวดมาถึง งวดนั้นต้องกระทบยอดโดยอัตโนมัติโดยไม่ต้องมีการกระทำใด ๆ
- FR-02.6 ระบบต้องคำนวณสิทธิประโยชน์และส่วนลดใหม่ต่อแต่ละงวด ไม่ใช้ค่าของยอดเต็ม
- FR-02.7 ระบบต้องอนุญาตให้ลบชุดผ่อนทั้งชุดพร้อมยืนยัน และรองรับการย้อนกลับ

### FR-03 การจัดการกระเป๋าเงิน
- FR-03.1 ยอดคงเหลือต้องเป็นผลลัพธ์ของการคำนวณเสมอ ไม่ใช่ค่าที่ผู้ใช้แก้โดยตรง
- FR-03.2 ระบบต้องเก็บ baseline (openingBalance / openingUnits) ครั้งแรกที่ตรวจสอบยอด
- FR-03.3 กระเป๋าลงทุนต้องคำนวณมูลค่าจากจำนวนหน่วยคูณราคาต่อหน่วย
- FR-03.4 ระบบต้องไม่ลบกระเป๋าที่มีธุรกรรมหรือรายการประจำอ้างอิงอยู่ แต่ต้องเปลี่ยนเป็นสถานะเก็บถาวรแทน
- FR-03.5 เมื่อลบกระเป๋า BNPL ระบบต้องลบแผนผ่อนของกระเป๋านั้นด้วย
- FR-03.6 ระบบต้องมีเครื่องมือให้ผู้ใช้ตรวจสอบและซ่อมยอดที่ไม่ตรง โดยเกณฑ์ความคลาดเคลื่อนคือ 0.01 บาท และ 1e-8 หน่วย

### FR-04 บัตรเครดิต
- FR-04.1 ระบบต้องคำนวณช่วงรอบบิลจากวันตัดรอบที่ผู้ใช้กำหนด และปรับวันให้ถูกต้องเมื่อเดือนนั้นไม่มีวันดังกล่าว
- FR-04.2 ระบบต้องรองรับวันครบกำหนด 2 โหมด: นับจากวันตัดรอบ (1–60 วัน) และวันที่คงที่ของเดือน (1–31)
- FR-04.3 ในโหมดวันที่คงที่ ถ้าวันครบกำหนดตรงเสาร์ อาทิตย์ หรือวันหยุดธนาคาร ระบบต้องเลื่อนย้อนหลังจนพบวันทำการ
- FR-04.4 ผู้ใช้ต้องปิดการเลื่อนวันหยุดได้ และเพิ่มวันหยุดของตัวเองได้
- FR-04.5 ยอดค้างชำระของรอบต้องเท่ากับยอดใช้จ่ายในรอบลบยอดที่ชำระแล้ว และต้องไม่ต่ำกว่า 0
- FR-04.6 การชำระที่นับเข้ารอบใดรอบหนึ่ง คือรายการที่มี statementId ตรงกัน หรือมีวันที่อยู่หลังวันตัดรอบและไม่เกินวันครบกำหนด
- FR-04.7 ระบบต้องแจ้งเตือนบัตรที่ครบกำหนดภายใน 3 วัน และต้องไม่แจ้งถ้าตรวจพบการชำระแล้ว
- FR-04.8 การชำระบัตรต้องรองรับกรณีมีส่วนลด โดยแยกยอดที่ตัดจากบัตรกับเงินที่จ่ายจริง
- FR-04.9 แหล่งเงินที่ใช้ชำระบัตรต้องไม่ใช่บัตรเครดิตหรือ BNPL

### FR-05 สิทธิประโยชน์บัตรเครดิต
- FR-05.1 ผู้ใช้ต้องสร้างกฎสิทธิประโยชน์ได้เองผ่านตัวช่วย 3 ขั้น
- FR-05.2 เมื่อบันทึกรายจ่ายบนบัตร ระบบต้องแสดงกฎที่เข้าเงื่อนไขทั้งหมด
- FR-05.3 ถ้าผู้ใช้ไม่เลือกเอง ระบบต้องเลือกชุดกฎที่ให้ผลตอบแทนสูงสุดโดยอัตโนมัติ
- FR-05.4 ระบบต้องไม่เลือกกฎที่ใช้สิทธิ์เต็มเพดานแล้ว
- FR-05.5 การคำนวณสิทธิประโยชน์ต้องอ้างอิงยอดก่อนหักส่วนลดทันทีเสมอ
- FR-05.6 ถ้ากฎให้ส่วนลดทันที ระบบต้องลดยอดธุรกรรมจริงและเก็บยอดเดิมไว้
- FR-05.7 ข้อมูลสิทธิประโยชน์ที่บันทึกลงธุรกรรมต้องถูกย่อให้เหลือเฉพาะฟิลด์ที่จำเป็น
- FR-05.8 ผู้ใช้ต้องดูได้ว่ากฎแต่ละข้อมีรายการใดถูกนับไว้บ้าง และเหลือเพดานเท่าไรรายร้าน/ช่องทาง

### FR-06 การเงินร่วมกับผู้อื่น
- FR-06.1 ผู้ใช้ต้องระบุได้ว่ารายจ่ายหนึ่งรายการเป็นการจ่ายแทนคนอื่นบางส่วน
- FR-06.2 รายงานและงบประมาณต้องนับเฉพาะส่วนของผู้ใช้เอง ไม่ใช่ยอดที่จ่ายออกทั้งหมด
- FR-06.3 ยอดคงเหลือของกระเป๋าต้องลดลงตามยอดที่จ่ายจริงทั้งหมด
- FR-06.4 เงินที่ได้รับคืนต้องไม่ถูกนับเป็นรายได้ในการคำนวณอัตราการออม
- FR-06.5 ระบบต้องแสดงสถานะการรับคืน 4 สถานะ: ยังไม่ได้รับ ได้บางส่วน ครบแล้ว และเกิน
- FR-06.6 ถ้าผู้ใช้บันทึกยอดรับคืนเกินยอดค้าง ระบบต้องเตือนและให้ยืนยันอีกครั้งก่อนบันทึก
- FR-06.7 การหารบิลต้องแบ่งเงินให้ผลรวมตรงกับยอดจริงเสมอ ไม่มีเศษหายหรือเกิน
- FR-06.8 ผู้ใช้ต้องจัดลำดับการคิดค่าบริการ ภาษี และส่วนลดได้เอง
- FR-06.9 ร่างบิลที่ยังไม่บันทึกต้องถูกเก็บไว้อัตโนมัติและกู้คืนได้เมื่อกลับเข้ามาใหม่
- FR-06.10 เงินให้ยืมต้องลดยอดกระเป๋าทันทีโดยไม่ถูกนับเป็นรายจ่าย และการรับคืนต้องเพิ่มยอดกลับ

### FR-07 การวางแผน
- FR-07.1 งบประมาณต้องคำนวณจากธุรกรรมที่เกิดขึ้นจริงแล้วเท่านั้น
- FR-07.2 ระบบต้องแสดงงบที่ใช้ได้ต่อวันจากยอดคงเหลือหารด้วยจำนวนวันที่เหลือในเดือน
- FR-07.3 ระบบต้องเตือนเมื่อใช้งบถึง 80% และ 100%
- FR-07.4 รายการรอจ่ายที่ยังไม่ชำระต้องถูกกันออกจากยอดเงินพร้อมใช้
- FR-07.5 รายการประจำต้องรองรับ 2 รูปแบบความถี่: ทุก N วัน และวันที่กำหนดของทุกเดือน
- FR-07.6 เมื่อรายการประจำถึงกำหนด ระบบต้องแสดงบนหน้าหลักพร้อมปุ่มบันทึกและปุ่มข้าม
- FR-07.7 ถ้ารายการประจำเลยกำหนดหลายรอบ ระบบต้องแสดงจำนวนรอบที่ค้าง

### FR-08 การวิเคราะห์
- FR-08.1 ระบบต้องคำนวณคะแนนสุขภาพการเงินจาก 3 องค์ประกอบ: อัตราการออม 50% ภาระหนี้ 30% และเงินสำรอง 20%
- FR-08.2 ระบบต้องแสดงที่มาของคะแนนได้เมื่อผู้ใช้ร้องขอ
- FR-08.3 ระบบต้องให้คำแนะนำอัตโนมัติได้ถึง 16 ประเภท และผู้ใช้ต้องปิด เลื่อน หรือให้คะแนนคำแนะนำได้
- FR-08.4 คำแนะนำต้องถูกคำนวณใหม่เมื่อข้อมูลเปลี่ยน หรืออย่างช้าทุก 4 ชั่วโมง
- FR-08.5 คำแนะนำที่ผู้ใช้ปิดไปแล้วต้องไม่กลับมาภายใน 30 วัน
- FR-08.6 ระบบต้องแสดงรายงานอย่างน้อย 8 มุมมอง และเลือกดูย้อนหลังได้ 6 เดือน

### FR-09 การเก็บรักษาข้อมูล
- FR-09.1 ข้อมูลทั้งหมดต้องถูกเก็บในเครื่องผู้ใช้และใช้งานได้เต็มรูปแบบโดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต
- FR-09.2 ทุกการบันทึกต้องถูกตรวจสอบด้วยการอ่านกลับเพื่อยืนยันว่าข้อมูลเขียนสำเร็จ
- FR-09.3 ระบบต้องไม่บันทึกข้อมูลก่อนที่การโหลดข้อมูลเดิมจะเสร็จสมบูรณ์
- FR-09.4 เมื่อพื้นที่จัดเก็บเต็ม ระบบต้องพยายามคืนพื้นที่จากข้อมูลสำรองอัตโนมัติก่อน แล้วจึงแจ้งผู้ใช้
- FR-09.5 ระบบต้องแสดงให้ผู้ใช้เห็นว่าข้อมูลส่วนใดใช้พื้นที่เท่าไร และให้คืนพื้นที่ได้เอง
- FR-09.6 การส่งออกต้องได้ไฟล์ JSON ที่มีข้อมูลครบทุกชุดพร้อมหมายเลขเวอร์ชันโครงสร้าง
- FR-09.7 การนำเข้าต้องผ่านการตรวจสอบและแสดงตัวอย่างให้ผู้ใช้ยืนยันก่อนเสมอ
- FR-09.8 การนำเข้าต้องข้ามรายการที่ไม่ถูกต้องแทนการล้มเหลวทั้งไฟล์ และต้องรายงานว่าข้ามอะไรไปบ้าง
- FR-09.9 ระบบต้องสร้างข้อมูลสำรองอัตโนมัติก่อนการนำเข้าทุกครั้ง
- FR-09.10 ไฟล์นำเข้าต้องมีขนาดไม่เกิน 10 เมกะไบต์
- FR-09.11 ระบบต้องกรองคีย์อันตรายและโค้ดที่ปฏิบัติการได้ออกจากไฟล์นำเข้า

### FR-10 ความปลอดภัยและความเป็นส่วนตัว
- FR-10.1 ผู้ใช้ต้องตั้งรหัสล็อกแอปได้ ความยาว 6–12 หลัก
- FR-10.2 รหัสต้องถูกเก็บเป็นค่าแฮชที่ผ่านการยืดคีย์ ไม่เก็บรหัสจริง
- FR-10.3 การใส่รหัสผิดตั้งแต่ครั้งที่ 5 ต้องมีการหน่วงเวลาที่เพิ่มขึ้นตามจำนวนครั้ง สูงสุด 5 นาที
- FR-10.4 ผู้ใช้ต้องใช้ Face ID หรือ Touch ID แทนรหัสได้ถ้าอุปกรณ์รองรับ
- FR-10.5 เมื่อแอปถูกสลับไปทำงานเบื้องหลัง ระบบต้องปิดบังหน้าจอทันที
- FR-10.6 ข้อมูลที่ส่งขึ้นคลาวด์ต้องถูกเข้ารหัสในเครื่องผู้ใช้ก่อนส่งเสมอ
- FR-10.7 เซิร์ฟเวอร์ต้องไม่สามารถถอดรหัสข้อมูลของผู้ใช้ได้
- FR-10.8 ระบบต้องแสดงกุญแจกู้คืนให้ผู้ใช้บันทึกไว้ และเตือนว่าหากสูญหายจะกู้ข้อมูลบนคลาวด์ไม่ได้
- FR-10.9 ข้อมูลที่ส่งขึ้นเซิร์ฟเวอร์เพื่อการแจ้งเตือนต้องมีเฉพาะตัวเลขที่จำเป็นต่อการตัดสินใจส่ง ไม่มีชื่อ ยอดเงิน หรือรหัสอ้างอิงใด ๆ
- FR-10.10 การลบบัญชีต้องยืนยันด้วยรหัสที่ส่งไปยังอีเมลของผู้ใช้ และต้องลบทั้งข้อมูลบนคลาวด์และในเครื่อง

### FR-11 การแจ้งเตือน
- FR-11.1 ผู้ใช้ต้องสร้างกฎแจ้งเตือนได้เอง โดยเลือกจากทริกเกอร์ 13 แบบ
- FR-11.2 ระบบต้องส่งแจ้งเตือนภายในหน้าต่างเวลา 15 นาทีนับจากเวลาที่ตั้งไว้
- FR-11.3 ระบบต้องไม่ส่งแจ้งเตือนซ้ำสำหรับเหตุการณ์เดียวกันในวันเดียวกัน
- FR-11.4 เมื่อผู้ใช้แตะแจ้งเตือน ระบบต้องเปิดหน้าจอที่เกี่ยวข้องโดยตรง
- FR-11.5 ถ้าแอปเปิดอยู่แล้ว ระบบต้องนำทางภายในแอปเดิมแทนการเปิดหน้าต่างใหม่
- FR-11.6 ผู้ใช้ต้องเลือกได้ว่าจะซ่อนจำนวนเงินในข้อความแจ้งเตือนหรือไม่

### FR-12 การนำทาง
- FR-12.1 ระบบต้องมีแท็บหลัก 5 แท็บที่เข้าถึงได้ตลอดเวลา
- FR-12.2 ปุ่มเพิ่มรายการต้องปรากฏเฉพาะหน้าที่เกี่ยวข้อง
- FR-12.3 หน้าที่ผู้ใช้เปิดค้างไว้ต้องถูกจดจำและเปิดกลับมาที่หน้าเดิมเมื่อเข้าแอปครั้งถัดไป
- FR-12.4 ปุ่มย้อนกลับของระบบปฏิบัติการต้องปิดหน้าซ้อนทีละชั้น ไม่ใช่ออกจากแอปทันที
- FR-12.5 ผู้ใช้ต้องปัดจากขอบซ้ายเพื่อย้อนกลับได้
- FR-12.6 การกดค้างปุ่มย้อนกลับต้องพากลับหน้าหลักทันที

## FS-3 ข้อกำหนดที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements)

### NFR-01 ประสิทธิภาพ
- ระบบต้องแสดงหน้าจอแรกโดยไม่รอ CSS นานเกิน 2.2 วินาที (24 รอบ × 50–120ms)
- ระบบต้องซ่อนหน้าจอเริ่มต้นภายใน 9 วินาทีเสมอ แม้มีข้อผิดพลาด
- Service Worker ต้องรอไฟล์โค้ดจากเครือข่ายไม่เกิน 900 มิลลิวินาที ก่อนใช้ไฟล์จาก cache
- ข้อจำกัดที่ทราบ: การแสดงรายการเป็นแบบ O(n) ต่อเดือน และการบันทึกเป็น O(n) ต่อครั้ง

### NFR-02 ความพร้อมใช้งานแบบออฟไลน์
- ทุกฟีเจอร์ยกเว้นราคาสินทรัพย์ การซิงก์ และการแจ้งเตือน ต้องทำงานได้เต็มรูปแบบโดยไม่มีอินเทอร์เน็ต
- ระบบต้องแสดงสถานะออฟไลน์ให้ผู้ใช้ทราบ
- Service Worker ต้อง precache ไฟล์ที่จำเป็นทั้งหมดตอนติดตั้ง

### NFR-03 ความทนทานต่อข้อผิดพลาด
- ข้อผิดพลาดของโมดูลหนึ่งต้องไม่ทำให้ทั้งแอปหยุดทำงาน
- ทุกจุดที่แตะ storage, DOM, และ network ต้องมีการดักข้อผิดพลาด
- การอ่านข้อมูลที่เสียหายต้องคืนค่าปลอดภัยแทนการล้มเหลว พร้อมแจ้งผู้ใช้

### NFR-04 ความเข้ากันได้
- รองรับเบราว์เซอร์ที่มี Web Crypto, Service Worker, และ localStorage
- ฟีเจอร์ที่ต้องการ API เพิ่มเติม (Speech, WebAuthn, Web Share, Clipboard) ต้องมี fallback หรือแจ้งผู้ใช้เมื่อไม่รองรับ
- ต้องทำงานได้ทั้งบนเบราว์เซอร์และในโหมด PWA ที่ติดตั้งแล้ว
- ต้องทำงานได้บน `file://` ตามที่ระบุในคอมเมนต์หัวไฟล์ `app_v2.js`

### NFR-05 ความปลอดภัยของข้อมูล
- ข้อมูลการเงินต้องไม่ถูกส่งออกนอกเครื่องในรูปแบบที่อ่านได้
- คีย์เข้ารหัสต้องไม่ถูกส่งขึ้นเซิร์ฟเวอร์
- การยืดคีย์ต้องใช้ PBKDF2 อย่างน้อย 210,000 รอบสำหรับ App Lock และ 310,000 รอบสำหรับ vault

### NFR-06 การบำรุงรักษา
- ทุกไฟล์ JavaScript ต้องมีหมายเลขเวอร์ชันสำหรับ cache-busting
- การเปลี่ยนแปลง UI ต้องผ่านทั้งโหมดสว่างและมืด
- ต้องมีเทสต์อัตโนมัติที่รันได้ด้วยคำสั่งเดียว

## FS-5 Acceptance Criteria สำหรับ QA (ตัวอย่างที่ตรวจสอบได้)

### AC-01 บันทึกรายจ่ายพื้นฐาน
- กำหนดให้มีกระเป๋าเงินสดยอด 1,000 บาท
- เมื่อบันทึกรายจ่าย 250 บาท หมวดอาหาร
- ต้องได้: ยอดกระเป๋าเป็น 750 บาท, ปรากฏในหน้ารายการวันนี้, ยอดรายจ่ายเดือนนี้เพิ่ม 250, และเด้งไปหน้ารายการ

### AC-02 ยอดเงินไม่พอ
- กำหนดให้กระเป๋าเงินสดยอด 100 บาท
- เมื่อพยายามบันทึกรายจ่าย 500 บาท
- ต้องได้: ข้อความ "ยอดเงินในกระเป๋าไม่เพียงพอ", ไม่มีการบันทึก, ข้อมูลในฟอร์มยังอยู่ครบ

### AC-03 วงเงินบัตรร่วม
- กำหนดให้บัตร A และ B อยู่ในกลุ่มวงเงินร่วม 50,000 บาท และมียอดใช้ไปแล้วรวม 48,000
- เมื่อพยายามบันทึกรายจ่าย 3,000 บาทบนบัตร A
- ต้องได้: ข้อความที่ระบุวงเงินคงเหลือพร้อมคำว่า "(วงเงินร่วม)"

### AC-04 ผ่อน 3 งวด
- เมื่อบันทึกรายจ่าย 1,000 บาทแบบผ่อน 3 งวด วันที่วันนี้
- ต้องได้: 3 ธุรกรรม ยอด 333.33 / 333.33 / 333.34 (ผลรวม 1,000 พอดี)
- งวดที่ 1 กระทบยอดทันที งวดที่ 2 และ 3 ไม่กระทบ
- เมื่อเปลี่ยนวันที่ระบบเป็นเดือนถัดไป งวดที่ 2 ต้องกระทบยอดโดยอัตโนมัติ

### AC-05 วันครบกำหนดชนวันหยุด
- กำหนดบัตรโหมด fixedDay วันที่ 13 เมษายน (วันสงกรานต์ในรายการวันหยุดเริ่มต้น)
- ต้องได้: วันครบกำหนดถูกเลื่อนย้อนหลังไปวันทำการก่อนหน้า

### AC-06 ค่าใช้จ่ายร่วม
- เมื่อบันทึกรายจ่าย 900 บาท ระบุ 3 คน
- ต้องได้: ยอดกระเป๋าลด 900, รายงานแสดงรายจ่าย 300, ยอดค้างรับ 600, สถานะ "ยังไม่ได้รับ"
- เมื่อบันทึกรับคืน 600 บาท: สถานะเปลี่ยนเป็น "ครบแล้ว" และยอดรายรับเดือนนี้ไม่เพิ่ม

### AC-07 นำเข้าไฟล์ที่มีข้อมูลเสีย
- เมื่อนำเข้าไฟล์ที่มี 10 ธุรกรรม โดย 3 รายการมีวันที่ผิดรูปแบบ
- ต้องได้: หน้าตัวอย่างแสดงว่าจะนำเข้า 7 รายการ พร้อมคำเตือน 3 บรรทัด

### AC-08 พื้นที่จัดเก็บเต็ม
- เมื่อ localStorage เต็มและมีข้อมูลสำรองในเครื่อง
- ต้องได้: ระบบลบข้อมูลสำรองแล้วบันทึกสำเร็จโดยผู้ใช้ไม่เห็นข้อผิดพลาด
- ถ้ายังไม่พอ: ข้อความ "พื้นที่จัดเก็บเต็ม กรุณาส่งออกข้อมูลก่อนเพิ่มรายการใหม่"

### AC-09 ปุ่มย้อนกลับของระบบ
- เมื่อเปิดหน้ารายละเอียดกระเป๋า แล้วเปิดฟอร์มแก้ไขกระเป๋าซ้อน แล้วกดปุ่มย้อนกลับของระบบ
- ต้องได้: ปิดเฉพาะฟอร์มแก้ไข ยังอยู่ที่หน้ารายละเอียดกระเป๋า
- กดอีกครั้ง: กลับหน้ากระเป๋า
- กดอีกครั้ง: ออกจากแอป

### AC-10 App Lock
- เมื่อตั้ง PIN แล้วปิดแอปและเปิดใหม่
- ต้องได้: จอล็อกปรากฏก่อนเห็นข้อมูล
- เมื่อใส่ผิด 5 ครั้ง: ต้องรอ 30 วินาที ก่อนลองใหม่ได้
- เมื่อสลับไปแอปอื่นแล้วกลับมา: จอปิดบังต้องปรากฏ

### AC-11 ซิงก์ข้ามอุปกรณ์
- เมื่อล็อกอินบนอุปกรณ์ที่ 1 และบันทึกรายการ
- แล้วล็อกอินบนอุปกรณ์ที่ 2 ด้วยบัญชีเดียวกันและกรอกกุญแจกู้คืนที่ถูกต้อง
- ต้องได้: ข้อมูลปรากฏครบบนอุปกรณ์ที่ 2
- เมื่อกรอกกุญแจผิด: ต้องได้ข้อความแจ้งว่าถอดรหัสไม่สำเร็จ ไม่ใช่ข้อมูลว่างเปล่า

### AC-12 แจ้งเตือน
- เมื่อสร้างกฎ "เตือนทุกวัน 20:00" และเปิดการแจ้งเตือน
- ต้องได้: ได้รับแจ้งเตือนภายใน 20:00–20:15
- เมื่อได้รับแล้วในวันนั้น ต้องไม่ได้รับซ้ำอีกในวันเดียวกัน
- เมื่อแตะแจ้งเตือน ต้องเปิดหน้าที่ระบุใน route ของกฎ
